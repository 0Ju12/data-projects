# warehouse — 공개 데이터로 질문을 세우고 표로 답하기 (전력 수요 · 데이터 직무 채용 공고)

데이터 분석가의 관점으로 공개 데이터를 다뤄 보려고 만든 프로젝트입니다.
한국전력거래소의 2025년 시간별 전국 전력 수요와 같은 시간대 기온·일사량, 그리고 매일 모으는 해외 채용 공고를 가지고 질문 8개를 세웠습니다.
질문마다 dbt 분석 표를 하나씩 만들어 답했고, 답을 읽을 때 조심해야 할 점도 함께 적었습니다.
수집·정제·품질 테스트·매일 실행은 이 답을 믿을 수 있게 하려고 갖춘 것입니다.

- **대시보드**: <https://0ju12.github.io/data-projects/warehouse/>
  - 분석 요약 · 전력 분석 · 채용 공고 분석 · 데이터 품질 · 부가 자료
  - 매일 06:17 KST 실행 뒤 다시 계산됩니다.
- **도구**: dbt-core + DuckDB, Python(모형 적합·수집), Airflow 3(DAG), GitHub Actions(매일 실행), pytest

## 분석 노트

### 1. 기온과 수요

평일만 골라 하루 평균 기온과 하루 평균 수요를 놓고 보면 U자 모양이 나옵니다. 처음에는 2℃ 구간별 평균표(`ana_demand_temp_bins`)로 모양을 확인했습니다. 가장 낮은 구간은 12~16℃였습니다.
그다음 "난방 구간 직선 + 냉방 구간 직선" 모형을 맞췄습니다. 꺾이는 기온 두 개는 0.5℃ 간격으로 모든 조합을 대 보고, 오차 제곱합이 가장 작은 쌍을 골랐습니다.
그 결과 난방은 13.0℃ 아래, 냉방은 17.5℃ 위에서 수요가 늘기 시작했고, 기울기는 냉방 쪽이 더 컸습니다. 하루 최대 수요로 맞추면 +1,100 / +2,150 MW, R² 0.86입니다.

- 쉬는 날은 수요 수준이 달라 빼고 맞췄습니다. 섞으면 같은 기온에서 점이 두 줄로 갈라집니다.
- 모형 적합은 numpy 없이 3×3 정규방정식을 직접 풀었습니다. 매일 실행 환경의 의존성을 dbt 하나로 유지하려는 선택이고, 알려진 기울기를 다시 찾아내는지 pytest로 확인합니다.
- 기온은 서울·부산·대전·광주 시간별 기온의 평균입니다. 계절에 따라 달라지는 일조 시간이나 생활 패턴도 기울기에 섞여 있으므로, "기온 1℃의 순수한 효과"라고 말하지는 않습니다.

### 2. 쉬는 날과 긴 연휴

날 종류는 평일 · 토요일 · 일요일·공휴일 셋으로 나눴습니다. 공휴일은 요일과 상관없이 일요일과 같은 묶음입니다.
공휴일은 `seeds/holidays_kr.csv`(2025년 관공서 공휴일 19일)로 관리합니다. 3월 3일·5월 6일·10월 8일 같은 대체공휴일과 6월 3일 대통령선거일도 넣었습니다. 처음 만든 날짜 차원에는 주말 표시만 있어서, 이런 날이 평일로 섞여 평일 평균을 끌어내리고 있었습니다.

긴 연휴는 앞뒤 14일 안의 평일, 쉬는 날과 각각 비교했습니다. 두 연휴 모두 보통 쉬는 날보다 8~9% 더 낮았습니다. 공장과 사무실이 며칠씩 함께 쉬기 때문으로 봅니다.
같은 저장소의 [전력 수요 예측](../power-demand/)에서 모든 모델이 크게 틀린 날이 연휴 직후 첫 평일(10/13)이었는데, 이 표가 그 이유를 수치로 보여 줍니다. 전날 값이 연휴 수요라서 어제 값을 쓰는 모델이 틀리는 것입니다.

### 3. 하루 중 최대 시각

계절별 평일 시간대 평균(`ana_demand_hour_profile`)을 그려 보면 겨울에는 오전 8~9시대에 한 번 솟고, 여름에는 오후 내내 올라 18시대에 가장 높습니다.
시각은 그 한 시간의 시작으로 적었습니다. 원본의 '18시'는 17:00~18:00 구간이라 17시대입니다.
12시대는 모든 계절에 한 번 꺼집니다. 점심시간입니다.

### 4. 상위 10일

10일 모두 평일이고, 무더위가 며칠 이어진 두 주(7/7~9, 8/18~29)에 몰려 있습니다. 같은 기온이라도 더위가 며칠째 이어진 날이 더 높은지(누적 더위), 습도가 영향을 주는지는 아직 확인하지 않았습니다.

### 5. 봄 한낮

3번에서 본 점심시간 감소가 봄에는 유난히 깊습니다. 이를 수치로 보려고 "평일 12~13시 수요가 그날 새벽 최저보다 낮은 날"을 월별로 셌습니다. 4월이 14일로 가장 많았고, 3월 8일·11월 6일이 뒤를 이었습니다. 여름에는 한낮이 새벽보다 21~33% 높아 이런 날이 없습니다.
냉난방이 적은 계절에, 전력망에 잡히지 않는 태양광이 낮 수요를 줄이는 현상과 맞는 모양입니다. 처음에는 일사량 자료가 없어 원인이라고 말하지 못했고, 6번에서 일사량을 붙여 확인했습니다.

### 6. 일사량을 붙여 확인한 봄 한낮 감소

5번의 가설은 "전력거래소가 계량하지 않는 태양광(자가용·소규모)이 맑은 날 한낮 수요를 깎는다"입니다. 가설이 맞다면 같은 계절 안에서도 맑은 날 한낮 수요가 더 낮아야 하고, 해가 진 뒤에는 맑음과 흐림의 차이가 없어야 합니다.

- **자료**: Open-Meteo 과거 자료에서 서울·부산·대전·광주의 2025년 시간별 일사량(수평면, W/m²)과 운량을 받아 평균했습니다(`data/solar_2025.csv`). Open-Meteo의 일사량은 그 시각 직전 한 시간 평균이라, 수요의 '끝 시각'과 맞춥니다(시작 시각으로 맞추면 한낮 창이 한 시간 밀립니다). 평일마다 한낮 일사량이 붙었는지는 dbt 테스트로 확인합니다.
- **같은 달끼리 비교**: 달마다 평일을 한낮 일사량 순으로 셋으로 나눴습니다(`ana_solar_terciles`). 12개월 모두 가장 맑은 3분의 1이 가장 흐린 3분의 1보다 '한낮 수요 ÷ 새벽 최저'가 낮았습니다. 여름에는 맑은 날이 더 덥지만(냉방이 늘지만) 그래도 낮았습니다.
- **통제 변수를 하나씩 넣으면**: 일사량만 넣으면 100 W/m²당 −1,613 MW, 달별 절편을 넣으면 −2,044 MW, 기온까지 넣으면 −2,704 MW입니다. 기온을 넣을수록 커지는 이유는, 여름에는 맑은 날이 더 더워 냉방 수요가 늘면서 태양광 효과를 가리기 때문입니다.
- **회귀**: 한낮 수요 = 달별 절편 + 새벽 최저 + 냉방(한낮 기온 24℃ 위) + 난방(16℃ 아래) + 일사량. 일사량 100 W/m²마다 −2,704 MW(표준오차 144, R² 0.91)였습니다. 같은 식을 해가 진 20~23시 수요에 맞추면 +11 MW(표준오차 83)로 0과 구분되지 않습니다. 흐린 날은 원래 활동이 많아 수요가 높다는 설명이라면 저녁에도 차이가 나야 하므로, 이 대조군이 가설 쪽을 지지합니다.
- **계절별**: 겨울 −4,088, 봄 −2,353, 여름 −1,998, 가을 −3,405 MW/100 W/m²입니다. 겨울이 큰 이유는 해가 낮을 때 기울어진 패널이 수평면보다 빛을 더 받기 때문일 수 있고, 여름이 작은 이유는 높은 기온에서 패널 효율이 떨어지기 때문일 수 있지만, 둘 다 확인하지는 않았습니다.

읽을 때 조심할 점:
- 흐린 날 낮에 조명을 더 켜는 효과는 같은 시간대에 겹쳐 떼어 내지 못했습니다. 다만 조명만으로 수천 MW 차이를 설명하기는 어렵다고 봅니다.
- 일사량은 네 도시 수평면 값의 평균입니다. 실제 태양광 설비는 전남·전북·충남 등에 많고 패널이 기울어 있어, 계수의 크기를 '설비 용량'으로 바꿔 읽지 않습니다.
- 계량되지 않는 태양광 규모에 대한 전력거래소의 공식 추정치와는 대조하지 않았습니다.
- 모형 적합은 1번과 같이 numpy 없이 정규방정식을 직접 풉니다(달 더미 12개 + 4개 변수). 알려진 계수를 다시 찾아내는지 pytest로 확인합니다.

### 7·8. 데이터 직무 공고의 기술

Remote OK와 Arbeitnow 공개 피드에서 매일 공고를 받습니다. 공고 제목으로 데이터 엔지니어·분석가·사이언티스트를 나누고, 직무별로 기술 이름이 한 번이라도 나온 공고의 비율을 냈습니다.
SQL은 세 직무 모두 위쪽에 있습니다. 엔지니어 공고는 Spark·Databricks·Airflow·Terraform·dbt처럼 처리와 인프라 도구가 넓게 나오고, 분석가 공고는 SQL 다음이 Python과 Tableau·Power BI입니다.

읽을 때 조심할 점:
- 107건, 1주일치입니다. 비율 하나가 공고 몇 건에 따라 크게 움직이므로, 순위가 바뀌는지 몇 주 더 쌓아 보고 판단합니다.
- 대부분 Arbeitnow(독일어권 중심) 공고입니다. 국내 채용 시장을 말해 주지 않습니다.
- 기술 사전(`seeds/skills.csv`, 50개)에 Excel·통계·A/B 테스트가 없습니다. 분석가 공고의 기술 수가 적게 나온 데는 사전의 빈틈도 섞여 있습니다.
- 공고 본문은 저장하지 않고 받을 때 사전으로만 훑기 때문에, 사전을 고쳐도 지난 공고는 다시 셀 수 없습니다. 그래서 어느 판의 사전으로 뽑았는지를 행마다 적어 둡니다.
- 급여를 적은 데이터 직무 공고가 0건이라 급여는 분석하지 않았습니다.

## 분석을 믿을 수 있게 만든 장치

```
demand.csv ─ stg_demand_wide ─ int_demand_hourly ─┬─ fct_demand_hourly ─ fct_demand_daily ─┬─ ana_demand_* · ana_peak_* · ana_holiday_effect
weather.csv ─ stg_weather ────────────────────────┘        └ dim_date ← holidays_kr (seed) ─┘  ana_noon_dip_monthly
solar_2025.csv ─ stg_solar ─────────────────────────────────────────────────────────────── ana_solar_daily ─ ana_solar_terciles · ana_solar_hour_profile
jobs.csv ─ stg_jobs ─ int_job_skills ─┬─ dim_skill ─ fct_skill_demand_weekly          ┌─ ana_role_skills
skills (seed) ────────────────────────┘  fct_job_postings ─ fct_jobs_daily ────────────┴─ ana_role_summary
```

| 층 | 하는 일 |
|---|---|
| staging (view) | 이름·형 정리만. 원본 파일은 복사하지 않고 그대로 읽음 |
| intermediate (view) | 날짜 × 24열 수요표를 시간별 행으로 풀기, 공고에서 기술 이름 펼치기 |
| marts (table) | 날짜·기술 차원과 시간·일·공고 사실 표 |
| analysis (table) | 질문 하나에 표 하나. 대시보드와 이 README의 숫자는 모두 여기서 나옴 |

모델 40개(분석 표 9개), dbt 테스트 123개, pytest 40개.

- **'24시'를 다음 날 0시로 넘기지 않습니다.** 원본의 `24시`는 그날 23:00~24:00 구간입니다. 끝나는 시각을 키로 쓰면 하루의 마지막 행이 다음 날로 넘어가 날짜별 집계가 한 시간씩 밀립니다. 그래서 시작 시각(`hour_start_kst`)을 키로 삼았고, "하루는 정확히 24행", "이웃 행 간격은 1시간" 테스트로 지킵니다.
- **분석 표에도 테스트를 붙였습니다.** (계절, 날 종류)마다 24시각이 다 있는지, 날 종류별 일수 합이 1년 일수와 같은지(분류에서 빠지는 날이 없는지), 비율이 0~100 안인지 봅니다. 그래프가 조용히 비틀어지는 것을 막으려는 것입니다.
- **공고의 태그는 쓰지 않습니다.** Remote OK의 처음 98건 중 `golang` 태그가 29건이었는데, 제목에 Go가 나오는 공고는 0건이었습니다. 간호사·채용 담당자 공고에도 붙어 있었습니다. 그래서 제목과 본문에서 직접 찾습니다.
- **급여 단위는 추측해 고치지 않습니다.** 시급, 월급, 천 단위 생략, 센트로 보이는 값이 섞여 있어 연봉으로 볼 수 있는 범위(1만~100만 달러)만 쓰고 나머지는 표시만 합니다.
- **수집 구간이 이어졌는지 기록합니다.** 두 피드 모두 "최근 N건"만 주므로, 이미 아는 공고가 나올 때까지 쪽을 넘깁니다(최대 8쪽). 끝까지 안 나오면 그 사이 공고를 놓친 것이므로 기록에 남기고 dbt가 경고합니다.
- **같은 날짜를 몇 번 돌려도 결과가 같습니다.** 날짜 파티션 내보내기는 임시 파일에 쓴 뒤 바꿔치기하고, 실행 기록도 같은 날짜 줄을 바꿔 씁니다.
- **dbt를 돌리기 전에 원본부터 봅니다.** 파일이 없거나 약속한 열이 빠지면 모델을 만들기 전에 멈추고, 그 실패도 실행 기록에 남깁니다.

## 부가 자료 (분석 질문에는 쓰지 않음)

같은 파이프라인에 붙여 둔 자료입니다. 대시보드 '부가 자료' 탭에 있습니다.

- **지진(USGS)·자연재해 경보(GDACS)**: 발표 뒤에 고쳐지는 기록을 덮어쓰지 않고 판을 쌓습니다(SCD 2형 스냅샷).
  - 지진은 수정 시각이 바뀌면, 재해는 경보 등급이 바뀔 때만 새 판을 만듭니다.
  - 월별 지진 집계는 바뀐 (월, 지역)만 다시 계산하는 증분 모델입니다. 매 실행마다 원본과 합계를 대조합니다.
- **거래소 시세·환율(업비트·코인베이스·Frankfurter)**: 하루 경계가 같은 거래소끼리만 묶습니다. 주말 환율은 직전 영업일 값으로 채우되, 채웠다는 표시를 남깁니다.
- **패키지 내려받기(PyPI·npm)**: 늦게 확정되는 통계라 최근 10일은 다시 받고, 7일이 다 차지 않은 주는 버립니다.

## 한계와 다음에 할 것

- **전력 자료가 2025년 한 해뿐입니다.** 해마다의 변화나 같은 계절끼리의 비교는 못 합니다. 매일 실행은 실행 날짜의 월·일을 2025년으로 옮겨 재실행 안전성만 확인합니다.
- **일사량 분석의 다음 단계**: 태양광 설비가 많은 지역(전남·전북·충남)의 일사량으로 바꿔 계수가 커지는지, 기울어진 면 일사량으로 겨울 계수가 줄어드는지 확인합니다. 전력거래소가 발표하는 계량되지 않는 태양광 추정치와도 대조할 계획입니다.
- **채용 공고**: 사전에 Excel·통계 용어를 넣고(새 공고부터 적용), 몇 주 쌓인 뒤 직무별 순위가 유지되는지 봅니다. 국내 공고는 키 없이 받을 수 있는 피드를 찾지 못해 아직 넣지 못했습니다.
- **Airflow는 `airflow dags test`로 끝까지 한 번 도는 것만 확인했습니다.** 매일 실행은 GitHub Actions가 같은 함수를 불러 합니다. 클라우드 웨어하우스로는 아직 옮기지 않았고, DuckDB 파일 하나로 돕니다.

## 실행

```bash
pip install -r requirements.txt
dbt build --profiles-dir .                        # 모델 + 분석 표 + 테스트 + 변경 이력
python -m wh.cli run --date 2026-11-13            # 원본 확인 → dbt build → 파티션 내보내기 → 실행 기록
python -m wh.cli report                           # docs/index.html (분석 표 + 기온 모형 적합)
python -m wh.cli collect-jobs                     # 채용 공고 피드 수집 (그 밖에 collect-market · collect-packages · collect-disasters)
python -m pytest -q                               # 40개
```

Airflow (dbt와 의존성이 부딪히지 않게 가상환경을 나눕니다):

```bash
python -m venv .dbt && .dbt/bin/pip install dbt-duckdb
pip install "apache-airflow>=3,<4" duckdb
export AIRFLOW_HOME=$PWD/airflow_home AIRFLOW__CORE__DAGS_FOLDER=$PWD/dags AIRFLOW__CORE__LOAD_EXAMPLES=False DBT_BIN=$PWD/.dbt/bin/dbt
airflow db migrate
airflow dags test warehouse_daily 2026-11-13
```

DAG `warehouse_daily`: `collect_* → check_sources → dbt_build → export_partition → record → report`. 작업은 얇은 껍데기이고 실제 일은 `wh/pipeline.py`의 함수가 하므로, 명령줄·테스트·Airflow가 같은 코드를 씁니다.
